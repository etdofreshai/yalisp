03

Language guide

Expressions, functions, and the core ideas that keep the language small, readable, and capable of describing its own implementation.

Implementation status: this repository ships a runnable WAT reader/evaluator, a Lisp-written bootstrap, and a bounded Lisp-written arithmetic compiler exercised in the YALISP Playground. Modules and a general compiler remain future work.

01 / Arithmetic

Calls use prefix notation

(* 6 7)  ; => 42
(- 6 1)  ; => 5

The executable seed supports these prefix integer operations. The Playground evaluates the same call shape through WebAssembly rather than displaying a precomputed result.

02 / Functions

Bind a lambda with define

(define factorial
  (lambda (n)
    (if (<= n 1)
      1
      (* n (factorial (- n 1))))))

(factorial 6)  ; => 720

This exact example uses forms implemented by the executable seed: a named recursive function, one parameter, a conditional, and ordinary prefix calls.

03 / Organization

Module syntax is not implemented

No YALisp module form, import form, loader, or module test exists in the current repository. Names such as assembly.module describe candidate WebAssembly module construction operations; they do not establish a YALisp source-module syntax.

04 / Self-description

Ask the Lisp compiler for a function payload

(cc.compile '(x) '((+ (* x x) 1)))
; => (param i32) (result i32)
;    (i32.add (i32.mul (local.get 0) (local.get 0))
;             (i32.const 1))

This exact cc.compile form is executed by the current seed after loading boot.lisp and compiler.lisp. The compiler is intentionally limited to one-parameter integer expressions; no general apply or eval function is exposed.

04

A REPL that grows into a compiler

The Playground starts with a WAT interpreter extended by boot.lisp. For its bounded compiler benchmark it then evaluates compiler.lisp, proving the first Lisp-written lowering stage on top of that same base.

read

Accept a Lisp form

The REPL receives a form and keeps the language’s syntax close to the implementation that understands it.

compile

Turn a form into executable work

The bootstrap compiler lowers YALisp forms through the small core and into the WebAssembly-oriented layers beneath it.

evaluate

Return a result and continue

The compiled form runs in the current environment, reports its value or error, and leaves the session ready for the next expression.

Bootstrapping keeps the trusted base small: the WAT seed implements the evaluator boundary, Lisp adds macros and library functions, and the first bounded compiler now lowers a proven arithmetic subset. Broader compilation and self-hosting remain future verified milestones.

06

Interfaces

YALisp’s interface contracts are organized as four layers. Each layer has a narrow job, so a program can be direct when it needs to be and portable when it can be.

01AssemblyWebAssembly primitives 02System interfacePortable system services 03DOMPortable documents and events 04SDLConcrete multimedia runtime

The Foundation page explains how the WebAssembly seed, bootstrap, and self-hosted compiler make these interfaces usable from YALisp.

05.1

Assembly

The assembly module is the direct translation layer. It exposes WebAssembly instructions to Lisp with as little policy or wrapping as possible. Use it when you need predictable low-level behavior. Its public names keep the WebAssembly shape: dots stay as dots and signedness suffixes become hyphenated Lisp names.

control

Control flow

Blocks, branches, calls, and return values provide the small set of primitives required to construct compiled control flow.

memory

Linear memory

Load, store, size, growth, fill, copy, and initialization make WebAssembly memory explicit and available to Lisp code.

numeric

Numeric instructions

Integer and floating-point arithmetic, comparisons, conversions, and bit-level operations map directly to WebAssembly numeric instructions.

Control and references

assembly.block, assembly.if, assembly.br-if, assembly.call, assembly.ref.null

Build structured control flow and work with WebAssembly references.

Locals, globals, and tables

assembly.local.get, assembly.global.set, assembly.table.grow, assembly.table.copy

Access execution state and indirect-call tables without hiding the runtime model.

Linear memory

assembly.i32.load, assembly.f64.store, assembly.memory.size, assembly.memory.grow

Read, write, and manage raw WebAssembly linear memory.

Scalar numeric types

assembly.i32.add, assembly.i64.div-s, assembly.f32.sqrt, assembly.f64.convert-i32-s

Use the integer and floating-point instruction families by their underlying type.

Vectors and atomics

assembly.v128.load, assembly.i32x4.add, assembly.f32x4.mul, assembly.i32.atomic.rmw.add

Access SIMD and shared-memory operations where the selected WebAssembly runtime supports them.

Module construction

assembly.type, assembly.func, assembly.memory, assembly.export

Describe the pieces of a WebAssembly module when YALisp needs to produce one directly.

Naming follows the underlying WebAssembly operation where practical—for example, an integer addition is exposed through the assembly interface rather than hidden behind a separate runtime.

05.2

System interface

The system interface is built on the WebAssembly System Interface. It gives programs a portable way to work with the outside world without binding the language to one operating system.

io

Streams and files

Read and write byte streams, work with files and directories, and report errors through a consistent capability-based interface.

time

Clocks and scheduling

Access monotonic and wall clocks, timers, and the timing facilities supplied by the WebAssembly host.

process

Arguments and environment

Receive command-line arguments, environment values, random bytes, and other process-scoped services where the host permits them.

This layer aims to track the WebAssembly system interface closely, so the same YALisp program can move between compatible runtimes with minimal adaptation.

05.3

DOM

The DOM Interface is the portable document-and-event contract for application structure, rendering surfaces, input, lifecycle, commands, and accessibility. It is not limited to the browser-native object model.

browser

Native DOM binding

A planned browser binding forwards the portable contract directly to native browser DOM nodes and events.

sdl

Lightweight tree binding

A planned SDL or bare-metal binding forwards it to YALisp’s in-memory document wrapper, SDL events, and SDL-backed presentation.

application-root

Proposed bootstrap

An illustrative helper would create one root surface, wire lifecycle and input, and select the correct binding. Its API remains to be defined.

This describes the intended contract and adapter model. No DOM binding or application-root helper is implemented in the repository yet.

05.4

SDL

SDL is the concrete multimedia profile for native YALisp programs. It supplies windows, accelerated 2D rendering, audio, input, and game-facing devices through a carefully scoped SDL 3 vocabulary.

video

Windows and displays

Create windows, observe size and pixel scale, manage fullscreen state, and react to display lifecycle changes.

render

2D frames and textures

Create renderers and textures, clear a frame, draw geometry or copies, and present output through SDL’s accelerated 2D path.

audio

Playback and capture

Open audio devices, move samples through streams, and control playback without tying programs to a platform mixer.

The SDL profile supplies concrete native multimedia capabilities beneath the DOM binding rather than replacing the portable DOM contract. Portable document code should target DOM; native games, demos, and tools may explicitly require SDL.

07

Game runtime

This is the intended architecture for game-facing runtime services above the existing interfaces. It defines responsibilities and timing relationships only; these facilities and their callable APIs are not implemented yet.

simulation update

Stable world steps

Gameplay and physics advance on a distinct update loop, commonly at a slower fixed cadence, so simulation remains predictable when rendering speeds up or slows down.

render update

Independently paced frames

Presentation samples the latest simulation state on its own cadence. It may interpolate visual state without changing the authoritative simulation step.

time

Clocks and time scale

Runtime time separates elapsed real time, simulation time, frame deltas, and a controlled time scale for pause, slow motion, or acceleration.

input and events

Intent enters the simulation

DOM or SDL events are normalized, buffered, and consumed at defined update boundaries rather than coupling gameplay directly to platform callbacks.

graphics and assets

Sprites, sheets, and resources

Game-facing primitives cover sprites and sprite sheets alongside loading, ownership, reuse, and release of textures, audio, and other assets.

networking

Synchronize with simulation

Future networking exchanges simulation inputs or state on simulation boundaries. It participates in that timing model instead of introducing a competing third update loop.

To be defined later: update scheduling APIs, interpolation and rollback policy, asset formats and lifetimes, input buffering rules, networking authority and transport, and the final names of every callable operation.
