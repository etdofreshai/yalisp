03

Language guide

Expressions, functions, and the core ideas that keep the language small, readable, and capable of describing its own implementation.

Implementation status: this repository currently ships the TypeScript website and its canonical YALisp example, not a runnable YALisp reader, evaluator, or compiler. The examples below stay within forms evidenced by that source and distinguish language goals from implemented behavior.

01 / Arithmetic

Calls use prefix notation

(* 6 7)  ; => 42
(- 6 1)  ; => 5

The published factorial example uses * and - in this position. These small expressions show the same call shape without claiming a broader numeric tower that is not implemented yet.

02 / Functions

Bind a lambda with define

(define factorial
  (lambda (n)
    (if (<= n 1)
      1
      (* n (factorial (- n 1))))))

(factorial 6)  ; => 720

This is the exact example maintained by the current site source: a named recursive function, one parameter, a conditional, and ordinary prefix calls.

03 / Organization

Module syntax is not implemented

No YALisp module form, import form, loader, or module test exists in the current repository. Names such as assembly.module describe candidate WebAssembly module construction operations; they do not establish a YALisp source-module syntax.

04 / Self-description

The compiler path is the current contract

source form
    ↓ read
syntax value
    ↓ compile
executable work
    ↓ run
result

This is a conceptual pipeline, not executable YALisp. The project intends to grow toward a compiler written in YALisp, but no callable compile, apply, or eval form is implemented or tested in this repository today.

04

A REPL that grows into a compiler

YALisp’s core REPL is a bootstrapped compiler written in Lisp—eventually, in YALisp itself. The interactive prompt is therefore the first usable surface of the language and part of the path to a self-hosted implementation.

read

Accept a Lisp form

The REPL receives a form and keeps the language’s syntax close to the implementation that understands it.

compile

Turn a form into executable work

The bootstrap compiler lowers YALisp forms through the small core and into the WebAssembly-oriented layers beneath it.

evaluate

Return a result and continue

The compiled form runs in the current environment, reports its value or error, and leaves the session ready for the next expression.

Bootstrapping keeps the trusted base small: begin with the minimum low-level support required to run Lisp, then use Lisp to grow the compiler and the interactive environment. As the implementation matures, more of the language can live in YALisp rather than in a separate host runtime.

06

Reference interfaces

This documentation is the source of truth for YALisp interface contracts. The standard interface is organized as four layers. Each layer has a narrow job, so a program can be direct when it needs to be and portable when it can be.

01AssemblyWebAssembly primitives 02System interfacePortable system services 03HostRendering and interaction 04SDLConcrete multimedia runtime

The Foundation page explains how the WebAssembly seed, bootstrap, and self-hosted compiler make these interfaces usable from YALisp.

05.1

Assembly

The assembly module is the direct translation layer. It exposes WebAssembly instructions to Lisp with as little policy or wrapping as possible. Use it when you need predictable low-level behavior. Its public names keep the WebAssembly shape: dots stay as dots and signedness suffixes become hyphenated Lisp names.

control

Control flow

Blocks, branches, calls, and return values provide the small set of primitives required to construct compiled control flow.

memory

Linear memory

Load, store, size, growth, fill, copy, and initialization make WebAssembly memory explicit and available to Lisp code.

numeric

Numeric instructions

Integer and floating-point arithmetic, comparisons, conversions, and bit-level operations map directly to WebAssembly numeric instructions.

Control and references

assembly.block, assembly.if, assembly.br-if, assembly.call, assembly.ref.null

Build structured control flow and work with WebAssembly references.

Locals, globals, and tables

assembly.local.get, assembly.global.set, assembly.table.grow, assembly.table.copy

Access execution state and indirect-call tables without hiding the runtime model.

Linear memory

assembly.i32.load, assembly.f64.store, assembly.memory.size, assembly.memory.grow

Read, write, and manage raw WebAssembly linear memory.

Scalar numeric types

assembly.i32.add, assembly.i64.div-s, assembly.f32.sqrt, assembly.f64.convert-i32-s

Use the integer and floating-point instruction families by their underlying type.

Vectors and atomics

assembly.v128.load, assembly.i32x4.add, assembly.f32x4.mul, assembly.i32.atomic.rmw.add

Access SIMD and shared-memory operations where the selected WebAssembly runtime supports them.

Module construction

assembly.type, assembly.func, assembly.memory, assembly.export

Describe the pieces of a WebAssembly module when YALisp needs to produce one directly.

Naming follows the underlying WebAssembly operation where practical—for example, an integer addition is exposed through the assembly interface rather than hidden behind a separate runtime.

05.2

System interface

The system interface is built on the WebAssembly System Interface. It gives programs a portable way to work with the outside world without binding the language to one operating system.

io

Streams and files

Read and write byte streams, work with files and directories, and report errors through a consistent capability-based interface.

time

Clocks and scheduling

Access monotonic and wall clocks, timers, and the timing facilities supplied by the WebAssembly host.

process

Arguments and environment

Receive command-line arguments, environment values, random bytes, and other process-scoped services where the host permits them.

This layer aims to track the WebAssembly system interface closely, so the same YALisp program can move between compatible runtimes with minimal adaptation.

05.3

Host

The host module covers the interactive capabilities that are intentionally outside the system interface: windows, rendering surfaces, input devices, audio, and browser-style document APIs.

display

Windows and rendering

Create surfaces, draw frames, manage graphics resources, and present output through an SDL-like or browser-backed host.

input

Events and devices

Receive keyboard, pointer, touch, gamepad, window, and lifecycle events through one event-oriented interface.

document

DOM-style interaction

Create and update visual elements, respond to user actions, and render application interfaces when the host provides a document model.

Hosts may expose different backends, but their public YALisp surface should describe the same capabilities. Platform-specific extensions belong here, clearly marked as extensions.

05.4

SDL

SDL is the concrete multimedia profile for native YALisp programs. It supplies windows, accelerated 2D rendering, audio, input, and game-facing devices through a carefully scoped SDL 3 vocabulary.

video

Windows and displays

Create windows, observe size and pixel scale, manage fullscreen state, and react to display lifecycle changes.

render

2D frames and textures

Create renderers and textures, clear a frame, draw geometry or copies, and present output through SDL’s accelerated 2D path.

audio

Playback and capture

Open audio devices, move samples through streams, and control playback without tying programs to a platform mixer.

The SDL profile is an extension beneath the Host Interface, not a replacement for it. Portable editor and document code should target Host; native games, demos, and tools may explicitly require SDL.
