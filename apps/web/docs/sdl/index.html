Reference interfaces / 04

SDL

Native graphics,
sound, and input.

The SDL Interface is YALisp’s concrete native-media profile. It maps SDL 3’s windowing, accelerated 2D rendering, audio, and event facilities into explicit Lisp capabilities.

This is the normative YALisp SDL Interface contract. It uses SDL 3 as its implementation target while keeping platform handles and C data structures out of ordinary YALisp code.

01 / Model

One main loop,
explicit resources.

An SDL session owns initialized subsystems and runs on the application’s main thread. Windows, renderers, textures, audio streams, gamepads, and cursors are opaque resources with clear construction and disposal rules.

sdl.session

Named subsystem grant

Opening a session requests only the needed subsystems: video, audio, events, gamepad, haptic, or camera. A headless tool need not initialize video.

sdl.resource

Host-backed, language-owned

Resource values carry no raw pointer semantics. Closing a parent session invalidates its remaining children in a predictable, documented order.

sdl.event

Stable data at the boundary

SDL events are normalized into maps with a kind, timestamp, window identity, device identity, modifiers, and event-specific fields.

02 / 2D graphics

Windows contain.
Renderers draw.

The 2D profile maps SDL’s accelerated renderer directly: programs draw primitives and textures into a frame, then present it. It does not expose shaders, command buffers, or render passes.

sdl.video

display.list · window.create · window.size · window.pixel-size · window.title · window.fullscreen · window.show · window.hide · window.close

Window sizing distinguishes logical points from drawable pixels. Resize, display-scale, close-requested, focus, and visibility changes arrive through sdl.events.

sdl.render

renderer.create · renderer.vsync · frame.clear · frame.color · frame.line · frame.rect · frame.fill-rect · frame.geometry · frame.present

The default profile targets SDL’s accelerated 2D renderer. Frames are main-thread work and finish only when the program explicitly presents or discards them.

sdl.texture

texture.create · texture.from-pixels · texture.load · texture.update · texture.size · texture.blend · texture.color-mod · texture.alpha-mod · texture.copy · texture.close

Textures are renderer-local resources. Pixel upload format and access mode are explicit, so a program does not silently assume a platform pixel layout.

sdl.surface

surface.create · surface.load · surface.pixels · surface.pitch · surface.convert · surface.close

CPU-side images support import, conversion, procedural pixels, screenshots, and texture upload. Surfaces are not presentation targets.

03 / Audio

Samples move through
streams, not callbacks.

SDL 3’s stream-oriented audio model maps naturally to YALisp values: programs describe format and enqueue samples; the host handles device timing, conversion, and mixing.

01

Open a device

sdl.audio.open selects an output or capture device and reports the negotiated sample format, channel count, and frequency.

02

Create a stream

sdl.audio.stream.create creates a conversion-aware queue between a program format and device format. stream.put and stream.get exchange byte vectors.

03

Control playback

device.resume, device.pause, stream.available, stream.flush, and stream.clear make queue state explicit for games and interactive media.

04 / Input and devices

Input is intent,
not keycodes alone.

sdl.events

event.poll · event.wait · event.subscribe · event.flush · event.enabled

Events cover quit, window lifecycle, keyboard, text editing and input, pointer motion and buttons, wheel, touch, pen, drop, clipboard, audio device, and render-device events.

sdl.keyboard

keyboard.state · keyboard.modifiers · text-input.start · text-input.stop · key.name

Physical keys, logical keys, and text composition are separate values. This preserves international input and editor behavior.

sdl.pointer

pointer.position · pointer.relative-mode · pointer.capture · cursor.create · cursor.set · cursor.show

Pointer coordinates are reported in the target window’s logical coordinate space; the event carries device and button state.

sdl.gamepad

gamepad.list · gamepad.open · gamepad.axis · gamepad.button · gamepad.rumble · gamepad.close

Controllers use SDL’s standardized gamepad layout when available. Connection and remapping changes remain ordinary events.

05 / 3D and GPU

Scenes become commands.
Passes make work explicit.

Programs that need 3D graphics or compute request the separate sdl.gpu capability. This low-level profile follows SDL 3’s GPU workflow: create reusable resources and pipelines, record copy, render, or compute passes into command buffers, then submit them. Cameras, transforms, meshes, materials, and scene graphs remain application or library policy.

sdl.gpu.device

device.create · window.claim · swapchain.configure · command-buffer.acquire · command-buffer.submit · command-buffer.cancel · device.wait-idle · device.close

A device selects a supported SDL GPU backend and shader format. Window presentation is an explicit claim; offscreen GPU work does not require a window.

sdl.gpu.resource

shader.create · graphics-pipeline.create · compute-pipeline.create · buffer.create · texture.create · sampler.create · transfer-buffer.create · resource.close

Shaders, pipelines, buffers, textures, samplers, and transfer buffers are opaque device-owned resources with explicit usage and release.

sdl.gpu.transfer

transfer-buffer.map · transfer-buffer.unmap · copy-pass.begin · buffer.upload · texture.upload · buffer.copy · texture.copy · buffer.download · texture.download · mipmaps.generate · copy-pass.end

CPU data crosses through transfer buffers. Upload, copy, download, and mipmap commands are recorded rather than performed synchronously.

sdl.gpu.render

swapchain.acquire · render-pass.begin · graphics-pipeline.bind · vertex-buffer.bind · index-buffer.bind · vertex-sampler.bind · fragment-sampler.bind · viewport.set · scissor.set · uniform.vertex.push · uniform.fragment.push · draw · draw-indexed · draw-indirect · render-pass.end

A render pass declares its color and optional depth-stencil targets. Pipeline and resource bindings are pass-local and must be set before drawing.

sdl.gpu.compute

compute-pass.begin · compute-pipeline.bind · sampler.bind · storage-buffer.bind · storage-texture.bind · uniform.push · dispatch · dispatch-indirect · compute-pass.end

Compute is part of the same command-buffer model and may alternate with copy and render passes when their resource dependencies permit it.

sdl.gpu.sync

command-buffer.submit-with-fence · fence.ready · fence.wait · fence.close · debug-group.push · debug-label · debug-group.pop

Fences make completion observable for readback and reuse. Debug labels preserve useful names in platform GPU tooling without leaking native handles.

The SDL 3 GPU API is the provenance for this profile. YALisp preserves its resource ownership, pass ordering, and submission model while presenting opaque values and Lisp-shaped arguments.

06 / Profiles and boundaries

Choose the smallest
capability that fits.

host

Portable interactive applications

Use the Host Interface for documents, editor layout, accessibility, commands, and backend-independent scenes.

sdl

Native games and media tools

Use SDL when a program intentionally needs native windows, frame timing, textures, audio devices, or controller input.

assembly

Direct runtime construction

Use Assembly only for WebAssembly-level work. SDL does not expose its C ABI or pointers through this contract.

SDL-specific behavior is never ambient. A library declares sdl.video, sdl.render, sdl.gpu, or another required capability, and a host must grant it before the library can create a native effect.
